# FilmPipe --- техническое задание

## 1. Цель проекта

FilmPipe --- локальное приложение для автоматической обработки сканов
фотоплёнки.

Основной сценарий:

``` text
скан негатива → FilmPipe → автоматическая обработка → набор готовых изображений
```

Пользователь загружает один или несколько отсканированных кадров,
выбирает параметры и режимы обработки и запускает задачу. Система
самостоятельно выполняет этапы обработки и предоставляет результаты для
просмотра и экспорта.

На первом этапе основной фокус --- **35-мм чёрно-белая негативная
плёнка**. Система должна работать полностью локально.

## 2. Цель первой итерации

Первая рабочая версия должна доказать сценарий:

``` text
RAW/исходный скан ч/б негатива
→ автоматическая нормализация и конвертация
→ технически корректный позитив
→ просмотр / экспорт
```

Для разработки физический сканер не требуется. В качестве тестовых
данных допускается использовать открытые сканы негативов из интернета.

### Definition of Done

Пользователь может:

1.  открыть локальное приложение;
2.  загрузить один или несколько негативов;
3.  выбрать режим `bw`;
4.  запустить обработку;
5.  получить технически корректный позитив каждого успешно обработанного
    изображения;
6.  сравнить исходник и результат;
7.  скачать результаты;
8.  получить понятную ошибку, если конкретный этап или изображение не
    удалось обработать.

AI-реставрация, colorization и generative processing не обязательны для
первой итерации, но архитектура не должна препятствовать их последующему
добавлению.

## 3. Основной архитектурный принцип

Обработка реализуется как **модульный processing pipeline**:

``` text
Input
↓
Validation / Decode
↓
Preprocessing
↓
Negative Conversion
↓
Tone / Exposure Normalization
↓
Defect Detection       [optional]
↓
Restoration            [optional]
↓
Postprocessing
↓
Mode Processing        [optional]
↓
Export
```

Каждый этап должен быть самостоятельным и заменяемым. Pipeline управляет
последовательностью обработки, но не зависит от деталей конкретной
AI-модели, ML-фреймворка или inference engine.

Не допускать распространения логики конкретного
OpenCV/ONNX/PyTorch/model provider по всему приложению.

## 4. Processor

Базовая единица pipeline --- `Processor`.

Конкретный контракт определяется при проектировании. Концептуально
processor должен:

-   принимать изображение и контекст обработки;
-   выполнять одну ограниченную задачу;
-   возвращать результат следующему этапу;
-   позволять отключение, если этап optional;
-   не зависеть от HTTP/API или UI;
-   явно сообщать об успешном результате или ошибке.

Примеры:

``` text
NegativeConverter
ToneNormalizer
ExposureNormalizer
DefectDetector
Restorer
Colorizer
GenerativeProcessor
Exporter
```

Single image и batch должны использовать один и тот же pipeline.

## 5. Non-destructive processing

Исходный файл --- immutable source. FilmPipe никогда не изменяет
исходный скан.

Результаты обработки являются отдельными производными артефактами:

``` text
original
positive
restored
colorized
creative
export
```

Пример:

``` text
scan_017_original.tif
scan_017_positive.tif
scan_017_restored.tif
scan_017_colorized.png
scan_017_creative_v1.png
```

Архитектура должна позволять хранить и сравнивать результаты разных
этапов.

## 6. Отказоустойчивость pipeline и частичные результаты

Pipeline не должен работать по принципу **«ошибка позднего этапа
уничтожает весь результат»**.

Если полезный промежуточный артефакт уже успешно создан, он должен
оставаться доступным при сбое последующего этапа.

Пример:

``` text
Original
↓
Negative Conversion   ✓
↓
Normalization         ✓
↓
Positive              ✓  ← полезный результат уже существует
↓
Defect Detection      ✓
↓
Restoration           ✗
```

В этом случае пользователь должен получить как минимум `positive` и
информацию о том, что Restoration завершился ошибкой.

### Обязательные этапы

Если ошибка произошла до получения минимально полезного результата ---
например, файл невозможно прочитать, декодировать или преобразовать в
позитив --- обработка конкретного изображения считается неуспешной.
Пользователь получает понятное сообщение об ошибке.

### Optional этапы

Ошибки AI-restoration, colorization, creative processing и других
optional processors должны:

-   фиксироваться;
-   отображаться пользователю;
-   не удалять уже созданные корректные артефакты;
-   по возможности не останавливать независимые ветки обработки.

### Batch

Ошибка одного кадра не должна останавливать обработку остальных кадров
batch.

Job может завершиться полным успехом, частичным успехом или ошибкой.
Конкретная модель статусов должна быть простой и определена при
проектировании.

## 7. Режимы обработки

Понятие **processing mode** закладывается сразу.

### `bw`

Основной режим MVP:

``` text
negative → basic processing → positive → optional restoration → B&W result
```

Сохраняет содержание исходного кадра.

### `colorize`

Будущий режим:

``` text
Clean Master → Colorization Processor → Colorized Result
```

В MVP может быть stub/not implemented.

### `creative`

Будущий генеративный режим:

``` text
Clean Master + text prompt → Generative Processor → Creative Result
```

Creative processing сознательно может изменять содержание фотографии. В
MVP может быть stub/not implemented.

## 8. Film processing и Creative processing

Эти ветки должны быть архитектурно разделены.

### Film processing

Задачи:

-   преобразовать негатив в позитив;
-   нормализовать изображение;
-   скорректировать тон/экспозицию;
-   обнаружить физические дефекты;
-   восстановить повреждённые участки;
-   максимально сохранить содержание исходного кадра.

Результат этой ветки --- **Clean Master**.

### Creative processing

Работает поверх Clean Master и может выполнять colorization, изменение
по prompt и будущие AI-преобразования.

Creative processing никогда не изменяет и не заменяет:

``` text
Original
Basic Positive
Clean Master
```

## 9. AI и ML

AI --- опциональный слой, а не фундамент FilmPipe.

Без AI система должна выполнять:

``` text
negative → technically correct positive
```

Первый AI-этап после базового pipeline:

``` text
image → Defect Detection → Mask → Restoration → Clean Master
```

Defect Detector должен обнаруживать физические дефекты плёнки: пыль,
волоски, царапины и другие локальные повреждения.

Результат detector --- mask или другое стандартизированное представление
дефектов.

Restorer работает локально по обнаруженным областям и по возможности не
изменяет остальные части изображения.

## 10. Абстракция AI providers

Конкретная AI-модель и inference backend не являются частью
бизнес-логики pipeline.

Предусмотреть заменяемые абстракции уровня:

``` text
DefectDetector
Restorer
InferenceProvider
GenerativeProcessor
```

Возможные будущие реализации:

``` text
OpenCV
ONNX Runtime
PyTorch
TensorRT
Diffusers
ComfyUI
Local API
другие реализации
```

Конкретные технологии данным ТЗ не фиксируются. Агент может выбрать
оптимальный вариант исходя из локального запуска, доступного железа,
простоты разработки, производительности, зрелости экосистемы и
заменяемости.

Приоритет --- простая расширяемая архитектура, а не абстракция ради
абстракции.

## 11. Целевое окружение

``` text
Ryzen 9 7900X
RTX 3060 12 GB
64 GB DDR5-6000
NVIDIA CUDA
```

Система проектируется как локальное desktop-oriented приложение. Backend
и processing engine не зависят от облачных сервисов. Будущие AI-модели
предполагается запускать локально.

## 12. Backend / Processing Engine

Предпочтительное направление:

``` text
Python
OpenCV
NumPy
локальный HTTP API
```

FastAPI, ONNX Runtime, PyTorch, TensorRT и другие технологии ---
кандидаты, а не жёсткие требования.

Агент должен выбрать минимально достаточный стек и обосновать
существенные архитектурные решения.

Processing Engine независим от API. Должна существовать возможность
концептуально выполнить:

``` text
process(image, options)
```

без HTTP-сервера.

В дальнейшем желательно добавить CLI:

``` bash
filmpipe process ./roll
```

## 13. Frontend

Frontend --- минимальный локальный desktop-oriented UI. Предпочтительное
направление --- React.

Первая версия:

-   загрузка одного изображения;
-   загрузка batch;
-   выбор режима обработки;
-   запуск processing job;
-   отображение состояния;
-   просмотр результата;
-   Original / Processed;
-   before/after;
-   отображение ошибок конкретного изображения или этапа;
-   доступ к успешно созданным частичным результатам;
-   скачивание результатов.

UI должен учитывать будущие режимы `B&W`, `Colorize`, `Creative`.

Для `creative` предусмотреть передачу текстового `prompt`, даже если
processor пока отсутствует.

Frontend не должен знать конкретную AI-модель, inference engine или ML
backend. Он работает только с контрактом FilmPipe API.

## 14. Batch processing

Система одинаково работает с:

``` text
1 image
N images
полной плёнкой ~36 кадров
```

Не создавать отдельную архитектуру для single и batch.

Для каждого изображения существуют собственные status, results и errors.

Ошибка одного изображения не уничтожает результаты остальных и не
останавливает весь batch без необходимости.

## 15. Processing Job

Обработка набора изображений концептуально является `Processing Job`.

Минимально Job содержит:

``` text
id
input files
processing options
selected modes
status
results
errors
```

В будущем могут добавляться:

``` text
AI configuration
prompt
model/provider
timings
metadata
```

Job должен позволять отличить успешную, частично успешную и полностью
неуспешную обработку.

Не переусложнять Job model заранее.

## 16. Логирование и диагностика

В системе должна присутствовать единая система логирования для
разработки и диагностики processing pipeline и будущих AI-модулей.

Минимально логировать:

-   создание и завершение processing job;
-   `job_id`;
-   начало и завершение обработки каждого изображения;
-   запуск и завершение значимых этапов pipeline;
-   ошибки processors;
-   ошибки чтения/декодирования файлов;
-   создание ключевых артефактов;
-   причины partial/failed результата.

Для технических ошибок сохранять достаточный диагностический контекст,
включая stack trace там, где это уместно.

Логирование не должно быть хаотично разбросано по приложению.
Использовать единый подход и стандартный logging mechanism выбранного
backend-стека.

### User-facing error и technical log

Пользователь получает короткое понятное сообщение, например:

``` text
Не удалось обработать scan_017.tif на этапе Restoration.
Базовый позитив сохранён и доступен.
```

Технический лог содержит подробности:

``` text
job_id
image_id / filename
processor
error
stack trace
timings / context при необходимости
```

Frontend не должен получать необработанный stack trace.

Для локального MVP достаточно разумного файлового/консольного
логирования. Отдельная observability-инфраструктура не требуется.

## 17. Результат обработки

После завершения job пользователь получает результаты выбранных режимов.

Пример:

``` text
roll/
├── original/
├── positive/
├── restored/
├── colorized/
└── creative/
```

В MVP реально заполненными могут быть только `original/` и `positive/`.

Не создавать пустые артефакты/директории для невыполненных processors
без необходимости.

При частичном успехе экспорт включает все корректно созданные
результаты.

Пользователь должен иметь возможность скачать batch, например
ZIP-архивом.

## 18. Форматы изображений

Архитектура не должна быть жёстко привязана к одному формату.

На первом этапе определить минимальный набор входных форматов на
основании реальных сканов.

При внутренней обработке приоритет --- сохранение максимума исходной
информации и отсутствие лишней lossy-компрессии.

Перед реализацией image pipeline исследовать и зафиксировать:

-   input formats;
-   internal representation;
-   bit depth;
-   output formats.

## 20. Следующий этап после MVP

После рабочего:

``` text
negative → positive
```

следующей отдельной задачей становится эксперимент с AI-restoration:

1.  подключить готовую pretrained-модель;
2.  запустить её локально;
3.  получить mask физических дефектов;
4.  визуализировать mask;
5.  передать mask в Restoration Processor;
6.  сравнить `positive` и `restored`.

На этом этапе качество важнее производительности. Оптимизация inference
выполняется после подтверждения работоспособности подхода.

## 21. Что сейчас НЕ делать

Не требуется:

-   обучение собственной нейросети;
-   создание собственного dataset;
-   distributed architecture;
-   микросервисы;
-   Kubernetes;
-   облачная инфраструктура;
-   авторизация;
-   пользовательские аккаунты;
-   база данных без доказанной необходимости;
-   сложная plugin system;
-   отдельная observability-платформа;
-   production deployment;
-   преждевременная CUDA/inference-оптимизация;
-   полноценный Creative AI;
-   полноценная colorization.

Не создавать абстракции только потому, что они потенциально могут
понадобиться.

## 22. Архитектурные инварианты

1.  Original никогда не изменяется.
2.  Basic pipeline работает без AI.
3.  Processing Engine не зависит от HTTP.
4.  Frontend не зависит от ML implementation.
5.  AI providers заменяемы.
6.  Processors можно добавлять и удалять без переписывания pipeline.
7.  Single и batch используют одну модель обработки.
8.  Creative processing отделён от технической обработки плёнки.
9.  Производные изображения сохраняются отдельно.
10. Уже созданный корректный артефакт не теряется из-за ошибки
    последующего этапа.
11. Ошибка optional processor не превращает успешно выполненную базовую
    обработку в полный failure.
12. Ошибка одного изображения не останавливает весь batch без
    необходимости.
13. Пользователь получает понятную ошибку, разработчик --- достаточный
    технический лог.
14. Архитектура позволяет добавить первый AI processor без переписывания
    MVP.

## 23. Принцип принятия технических решений

Если ТЗ не фиксирует реализацию, агент должен:

1.  выбрать наиболее простое решение, удовлетворяющее текущей задаче;
2.  учитывать дальнейшее подключение AI;
3.  не создавать инфраструктуру «на всякий случай»;
4.  использовать зрелые библиотеки вместо собственной реализации
    стандартных задач;
5.  явно фиксировать существенные технические решения;
6.  при нескольких разумных вариантах выбирать тот, который проще
    заменить в будущем.

Главный приоритет:

> Сначала получить работающий end-to-end pipeline на реальном негативе.
> Затем улучшать качество, AI и производительность.

## 24. Итоговый критерий успеха текущего этапа

Проект считается успешно запущенным, когда можно взять реальный открытый
скан чёрно-белого негатива и выполнить:

``` text
upload
↓
FilmPipe
↓
automatic processing
↓
technically correct positive
↓
preview
↓
download
```

без ручной обработки во внешнем редакторе.

Если последующий optional-этап завершился ошибкой, уже созданный позитив
остаётся доступным, ошибка отображается пользователю и фиксируется в
логах.

После этого отдельной следующей задачей подключается AI defect
detection/restoration.
